# SLO の基本（SRE 本 第 4 章）

出典：[Site Reliability Engineering, Chapter 4 - Service Level Objectives](https://sre.google/sre-book/service-level-objectives/)

## 3 行まとめ

- 何を測り（SLI）、どこを目指し（SLO）、外したらどうなるか（SLA）を分けて決める
- 指標は「測れるもの」ではなく「ユーザーが気にすること」から選び、平均ではなく分布（パーセンタイル）で見る
- 目標は 100% にせず、少なく・シンプルに・緩めから始めて、運用しながら締めていく

---

## 用語：SLI / SLO / SLA

| 用語 | 何か                                                     | 例                                         |
| ---- | -------------------------------------------------------- | ------------------------------------------ |
| SLI  | サービスレベルを定量的に表す指標                         | レイテンシ、エラー率、スループット、可用性 |
| SLO  | SLI の目標値（または範囲）                               | 検索リクエストの平均レイテンシ 100 ms 未満 |
| SLA  | SLO を満たせなかったときの「結果」を含むユーザーとの契約 | 未達なら返金・ペナルティ                   |

- **SLI**
  - 生の値をそのまま使うことは少なく、測定期間で集約して率・平均・パーセンタイルにする
  - 本当に測りたいものが測れないときは代理指標を使う（例：クライアント側のレイテンシの代わりにサーバー側のレイテンシ）
  - **可用性**は「サービスが使える時間の割合」。リクエストベースでは「正しい形式のリクエストのうち成功した割合」（yield）で定義することが多い。ストレージでは**耐久性**も重要
  - 99% を「2 nines」、99.999% を「5 nines」と呼ぶ
- **SLO**
  - `SLI ≤ 目標` または `下限 ≤ SLI ≤ 上限` の形で書く
  - SLO を公開しないと、ユーザーは勝手に期待値を作ってしまう
- **SLA**
  - SLO との見分け方：**「SLO を外したら何が起きる？」** 明示的な結果がなければ、それは SLO
  - SLA の中身はビジネス・法務の判断なので、SRE は通常作らない。SRE の役割は SLO を外して SLA の結果が発動しないようにすること

## SLI の選び方

### ユーザーが気にすることから選ぶ

- 測れる指標を全部 SLI にしない
  - 多すぎる → 大事な指標に注意が向かない
  - 少なすぎる → 重要な振る舞いを見逃す
  - 代表的な数個で足りる
- システムの種類ごとの典型的な SLI：

| システムの種類               | 主な SLI                                   | 問い                                                     |
| ---------------------------- | ------------------------------------------ | -------------------------------------------------------- |
| ユーザー向けのサービング     | 可用性、レイテンシ、スループット           | 応答できたか？何秒かかったか？何件さばけたか？           |
| ストレージ                   | レイテンシ、可用性、耐久性                 | 読み書きに何秒？必要なときに読める？データは残っている？ |
| ビッグデータ（パイプライン） | スループット、エンドツーエンドのレイテンシ | どれだけ処理できた？投入から完了まで何秒？               |
| すべてのシステム             | 正しさ                                     | 正しい答え・データ・分析を返したか？                     |

- 正しさはインフラよりデータの性質であることが多く、SRE の責任範囲外のことも多い。それでもシステムの健全性を示す指標として大事

### どこで測るか

- サーバー側（監視システム、ログ解析。例：HTTP 500 の割合）で測るのが自然
- ただし、クライアント側で測らないと見逃す問題がある
  - 例：バックエンドのレイテンシは良くても、ページの JavaScript が原因でユーザー体験が悪いことがある。「ブラウザでページが使えるようになるまでの時間」のほうがユーザー体験に近い

### 集約：平均ではなく分布で見る

- 「1 秒あたりのリクエスト数」も暗黙に集約している。1 秒ごとに測るのか、1 分の平均なのかで見えるものが変わる
  - 例：偶数秒に 200 req/s、奇数秒に 0 req/s → 平均は一定の 100 req/s と同じだが、瞬間的な負荷は平均の 2 倍
- レイテンシの平均はロングテールを隠す
  - 例：大半のリクエストは約 50 ms だが、5% は 20 倍遅い。平均だけ見ると一日中変化がないのに、実際は裾が大きく動いている
- パーセンタイルを使う
  - p99 / p99.9 → ありうる最悪ケース
  - p50（中央値）→ 典型的なケース
  - 応答時間のばらつきが大きいほど、体験はロングテールに左右される。高負荷時はキューイングでさらに悪化する
  - ユーザーは「ばらつきが大きいシステム」より「少し遅くても安定したシステム」を好む傾向がある。そのため高パーセンタイルだけを見るチームもある（p99.9 が良ければ典型ケースも良いはず、という考え方）
- 統計の落とし穴
  - コンピュータのデータは歪む（0 ms 未満の応答はない、タイムアウトを超えた成功はない）。だから平均と中央値が近いとは限らない
  - 正規分布だと確かめずに仮定しない。外れ値で動く仕組み（例：レイテンシが高いサーバーを再起動する）が、想定より頻繁に、または稀にしか動かなくなる

### SLI の定義を標準化する

毎回ゼロから考えなくて済むように、共通の定義をテンプレートにしておく。テンプレートどおりなら個別の SLI では書かなくてよい。

| 項目                       | 例                                        |
| -------------------------- | ----------------------------------------- |
| 集約の間隔                 | 1 分間の平均                              |
| 集約の範囲                 | クラスタ内の全タスク                      |
| 測定の頻度                 | 10 秒ごと                                 |
| 対象のリクエスト           | ブラックボックス監視ジョブからの HTTP GET |
| データの取り方             | 監視システムで、サーバー側で測定          |
| データアクセスのレイテンシ | 最後のバイトまでの時間                    |

## SLO の決め方

### 測れるものからではなく、ユーザーが気にすることから

- ユーザーが気にすることは測りにくい（または測れない）ことが多く、結局は近似になる
- それでも、測りやすいものから始めると役に立たない SLO になる
- 目標から逆算して SLI を選ぶほうがうまくいくこともある

### 定義には「どう測るか」と「どんな条件で有効か」を書く

```
99%（1 分間の平均）の Get RPC が 100 ms 未満で完了する（全バックエンドサーバーで測定）
```

分布の形が大事なら、複数段階の目標を置く：

```
90% の Get RPC が 1 ms 未満で完了する
99% の Get RPC が 10 ms 未満で完了する
99.9% の Get RPC が 100 ms 未満で完了する
```

ワークロードの性質が違うユーザーがいるなら、種類ごとに分ける：

```
スループット重視のクライアントの Set RPC の 95% が 1 秒未満で完了する
レイテンシ重視のクライアントの 1 kB 未満の Set RPC の 99% が 10 ms 未満で完了する
```

### 100% を目指さない

- 100% を求めると、新機能やデプロイの速度が落ちるか、高価で保守的な解決策が必要になる（またはその両方）
- 代わりに**エラーバジェット**（SLO を外してよい割合）を設けて、日次・週次で追う。上層部向けには月次・四半期でも見る
- エラーバジェットは「SLO を満たすための SLO」
- SLO 違反の割合とエラーバジェットの差を、リリースするかどうかの判断材料にする（詳しくは第 3 章）

### 目標値を選ぶときの教訓

目標値の選択はプロダクトやビジネスに影響するので、純粋に技術的な作業ではない。SRE は議論に参加して、リスクや実現性を助言する立場。

| 教訓                       | 理由                                                                                                                     |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 現在の性能を基準に選ばない | よく考えずに現状値を採用すると、英雄的な努力がないと守れず、大規模な再設計なしには改善できないシステムを抱えることになる |
| シンプルに保つ             | 複雑な集約は性能の変化を隠し、理解もしにくい                                                                             |
| 絶対を避ける               | 「無限に」スケール、「常に」使える、は非現実的。作るのに時間がかかり、運用は高く、ユーザーが満足する以上に良すぎる       |
| SLO はできるだけ少なく     | 優先度の議論でその SLO を持ち出して勝てないなら、持つ価値はない。「ユーザーの喜び」のように SLO にしにくい属性もある     |
| 完璧は後回し               | 緩い目標から始めて締めるほうが、厳しすぎて達成できないと分かってから緩めるより良い                                       |

- SLO はユーザーが気にすることを反映しているので、SRE と開発者の作業の優先度を決める強力なレバーになる
- 良い SLO は開発チームへの正当な強制力になる。攻めすぎた SLO は無駄な英雄的努力を生み、緩すぎる SLO は悪いプロダクトを生む

### SLO で制御ループを回す

1. SLI を監視・測定する
2. SLI を SLO と比べて、対応が必要か判断する
3. 必要なら、目標を満たすために何をすべきか考える
4. 実行する

例：レイテンシが上がっていて、このままだと数時間後に SLO を割る → CPU がボトルネックという仮説を確かめる → サーバーを増やして負荷を分散する。**SLO がなければ、対応すべきかどうか（いつ動くべきか）が分からない。**

### SLO は期待値を決める

SLO を公開すると、ユーザーはそのサービスが自分の用途に合うか判断できる。現実的な期待値を持ってもらうための戦術：

- **安全マージンを持つ**：外部に公開する SLO より厳しい内部 SLO を持つ。慢性的な問題に、外から見える前に対応できる。コストや保守性のために性能を少し落とす作り直しもしやすくなる
- **やりすぎない**：ユーザーは「宣言された SLO」ではなく「実際の性能」に依存する
  - 例：Google の Chubby（分散ロックサービス）は可用性が高すぎて、他サービスが過度に依存した。そこで四半期の中で本物の障害が起きず可用性が目標を下回らなかった場合は、意図的にシステムを止める計画停止を入れるようにした。これで不適切な依存をあぶり出す
  - 他の手段：一部のリクエストをスロットリングする、低負荷時に速くならないように設計する
- 期待値に対する達成度を見れば、性能・可用性・回復力に投資すべきか、それとも技術的負債の返済や新機能に時間を使うべきかを判断できる

## SLA の実際

- 違反時の結果やペナルティはビジネス・法務チームが決める。SRE は、SLA に含まれる SLO を達成できる可能性と難しさを伝える
- SLO の作り方の助言は SLA にも当てはまる
- ユーザーに公開する内容は保守的にする。対象が広いほど、後から変えたり消したりしにくい

## ロードマップの「学ぶ観点」との対応

| 観点                                  | 第 4 章で分かったこと                                                | 続きを学ぶ場所                                                                     |
| ------------------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 1. ユーザーの行動から始める           | 測れるものではなく、ユーザーが気にすることから選ぶ                   | —                                                                                  |
| 2. SLI の種類                         | システムの種類ごとの典型的な SLI。「鮮度」は本章では明示されていない | SRE Workbook「Implementing SLOs」                                                  |
| 3. どこで測るか                       | サーバー側が自然だが、クライアント側でしか見えない問題もある         | —                                                                                  |
| 4. 目標値は現状を測ってから決める     | ⚠️ 本章は「現在の性能を基準に選ばない」と言っている（下のメモ参照）  | SRE Workbook「Implementing SLOs」                                                  |
| 5. エラーバジェットの使い道           | 概念だけ（SLO を満たすための SLO、リリース判断の材料）               | SRE 本 第 3 章「Embracing Risk」、SRE Workbook                                     |
| 6. SLO アラートと原因アラートを分ける | 本章ではほぼ扱わない                                                 | SRE 本 第 6 章「Monitoring Distributed Systems」、SRE Workbook「Alerting on SLOs」 |

### メモ：観点 4 と「現在の性能を基準に選ばない」

矛盾ではなく、役割が違うと理解しておく。

- **現状を測る**のは、システムの限界や実力を知るため（何が無理なく出せるのか）
- **目標値を決める**根拠は、ユーザーが何を必要としているか
- 現状値をそのまま目標にすると、「今たまたま出ている数字」を守るために無理をすることになる

ロードマップの観点 4 は「現状を知らずに目標を決めない」と読み替えるのがよさそう。Workbook を読んだら改めて見直す。
