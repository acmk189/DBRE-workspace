## 3 行まとめ

- SLI は「良いイベント数 / 有効なイベント数」の比率で表す。0〜100% にそろえると、そのまま SLO とエラーバジェットに変換できる
- 最初の SLO は完璧でなくていい。まず測って置いてみて、フィードバックループで改善していく
- SLO は関係者の合意とエラーバジェットポリシーがあって初めて意思決定に使える。ないと、ただの指標で終わる

---

## SLO を意思決定に使うための前提条件

エラーバジェットで運用するには、次の状態になっている必要がある：

1. 関係者が SLO を承認している
2. SLO を守る担当者が、通常の状況で達成できると合意している
3. 組織がエラーバジェットを意思決定と優先度付けに使うとコミットしている（エラーバジェットポリシーとして明文化する）
4. SLO を見直すプロセスがある

これがないと、SLO は「報告用の KPI」になるだけで、何かを決める道具にならない。

## 信頼性の目標とエラーバジェット

- SLO は「ユーザーが満足するかどうか」の境目
  - SLO より上 → ほとんどのユーザーは満足している
  - SLO より下 → 不満が出始める、使うのをやめる
- 大事なのは最終的にユーザーの満足度。監視ではなくユーザーが信頼性を決める
- エラーバジェット = 1 − SLO
  - 例（自分で計算）：4 週間で 100 万リクエスト、SLO 99.9% → 1,000 件までは失敗してよい

---

## 何を測るか：SLI

### SLI は「良いイベント / 有効なイベント」で表す

例：

- 成功した HTTP リクエスト数 / 全 HTTP リクエスト数
- 100 ms 未満で成功した gRPC 呼び出し数 / 全 gRPC 呼び出し数
- 全データを使って返した検索結果の数 / 全検索結果の数（縮退して返したものも含む）
- 一定時間以内に更新されたデータを使った在庫確認の数 / 全在庫確認の数

この形にするメリット：

- 0% = 何も動いていない、100% = 何も壊れていない。直感的
- SLO の目標値やエラーバジェットにそのまま変換できる
- 形式がそろうと、ツールやダッシュボードを共通化しやすい

### コンポーネントの種類ごとの SLI メニュー

| 種類           | SLI        | 定義                                                                                              |
| -------------- | ---------- | ------------------------------------------------------------------------------------------------- |
| リクエスト駆動 | 可用性     | 成功したリクエストの割合                                                                          |
|                | レイテンシ | 閾値より速かったリクエストの割合                                                                  |
|                | 品質       | 縮退せずに返したレスポンスの割合（過負荷や依存先の障害で縮退運転するサービスの場合）              |
| パイプライン   | 鮮度       | 閾値より最近に更新されたデータの割合。理想はユーザーがデータを読んだ回数で数える                  |
|                | 正しさ     | 入力されたレコードのうち、正しい値が出力されたものの割合                                          |
|                | カバレッジ | バッチ：目標量以上のデータを処理できたジョブの割合 / ストリーム：時間内に処理できたレコードの割合 |
| ストレージ     | 耐久性     | 書き込んだレコードのうち、正しく読めるものの割合                                                  |

- **耐久性の注意**：ユーザーが欲しいデータは、保存しているデータのごく一部かもしれない。10 年分のデータのうち 99.99% が読めても、ユーザーが欲しい「今日の分」が読めなければ不満になる
- レイテンシも「p95 が何 ms」ではなく「閾値より速かった割合」で表す。こうすると可用性と同じ形でエラーバジェットを計算できる

### SLI の「仕様」と「実装」を分ける

- **仕様**：ユーザーにとって大事な結果。測り方には依存しない
  - 例：ホームページのリクエストのうち、100 ms 未満で読み込めた割合
- **実装**：仕様 + 測り方。1 つの仕様に複数の実装がありうる

| 測り方                                     | 長所                                           | 短所                                         |
| ------------------------------------------ | ---------------------------------------------- | -------------------------------------------- |
| サーバーログのレイテンシ                   | 手軽                                           | バックエンドに届かなかったリクエストを見逃す |
| ブラウザで JavaScript を実行するプローバー | リクエストがサーバー側に届かないエラーも拾える | 一部のユーザーだけに起きる問題は見逃す       |
| ページ内の JavaScript で計測して送信する   | ユーザー体験をいちばん正確に捉えられる         | 計測コードの追加や送信先の用意が必要         |

- 実装を比べる観点：**品質**（ユーザー体験をどれだけ正確に捉えるか）、**カバレッジ**（どれだけ多くのユーザーを捉えるか）、**コスト**
- 最初の SLI と SLO は正しくなくていい。いちばん大事なのは、まず何かを測り始めて、改善のフィードバックループを作ること

## 例：モバイルゲーム

- 構成
  - ユーザーのスマホ → ロードバランサ → API サーバー（ゲームプレイ）/ HTTP サーバー（ランキング表の Web ページ）
  - データ処理パイプラインがランキング表を生成する
- 選んだ SLI

| 対象                | SLI        | 仕様                                                           | 実装（測り方）                     |
| ------------------- | ---------- | -------------------------------------------------------------- | ---------------------------------- |
| API / HTTP サーバー | 可用性     | 成功したリクエストの割合（5xx 以外を成功とみなす）             | ロードバランサのメトリクス         |
| API / HTTP サーバー | レイテンシ | 閾値より速かったリクエストの割合                               | ロードバランサのメトリクス         |
| パイプライン        | 鮮度       | ランキング表から読んだレコードのうち、最近更新されたものの割合 | パイプラインが出すデータの更新時刻 |
| パイプライン        | 正しさ     | 既知のデータを投入して、正しい結果が読めた割合                 | 正しさを確かめるプローバー         |

- 直近の実測値を切りのいい数字にして、最初の SLO（starter SLO）にしている

## 時間窓を決める

| 窓の種類                             | 長所                                                                   |
| ------------------------------------ | ---------------------------------------------------------------------- |
| ローリング（例：直近 4 週間）        | ユーザーの体験に近い。月末の大障害を、ユーザーは月初になっても忘れない |
| カレンダー（例：月ごと、四半期ごと） | ビジネスの計画やプロジェクトの区切りと合わせやすい                     |

- 窓は週単位にすると、いつも同じ数の週末が含まれる
- 汎用には 4 週間のローリング窓が使いやすい。あわせて、週次のサマリーで作業の優先度を決め、四半期のレポートでプロジェクトを計画する
- 窓が短いほど早く判断でき、長いほど戦略的な判断に向く

## 関係者の合意を取る

3 者が合意すれば、いちばん難しいところは終わり：

| 誰が                   | 何に合意するか                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------------- |
| プロダクトマネージャー | この閾値がユーザーにとって十分。これを下回るのは許容できず、エンジニアの時間を使って直す価値がある |
| 開発者                 | エラーバジェットを使い切ったら、予算内に戻るまでユーザーへのリスクを下げる行動を取る               |
| 本番環境の担当チーム   | 英雄的な努力や過剰なトイル、燃え尽きなしにこの SLO を守れる                                        |

## エラーバジェットポリシー

- SLO からエラーバジェットが決まる。それを使うには「使い切ったときに何をするか」の方針が必要
- 主要な関係者全員の合意が必要。合意できないなら、SLO そのものを見直す
- 使い切ったときの行動の例：
  - 直近 4 週間の信頼性に関わるバグを最優先にする
  - SLO を満たすまで信頼性の改善だけに集中する（外部からの機能要望を断る承認つき）
  - 予算が戻るまで、特定の変更を止める（本番の凍結）
- 付録のポリシー例では「直近 4 週間でエラーバジェットを超えたら、P0 の問題とセキュリティ修正以外の変更とリリースを止める」としている
- ポリシーに書くこと：
  - 作成者・レビュアー・承認者
  - 承認日と次の見直し日
  - サービスの説明
  - 使い切ったときの行動
  - 計算方法や行動の妥当性で揉めたときのエスカレーション先
  - 読み手の経験に応じて、エラーバジェットの概要

## SLO を文書化する

SLO のドキュメントに書くこと：

- 作成者・レビュアー（技術的な正しさを確認した人）・承認者（ビジネス判断をした人）
- 承認日と次の見直し日
- サービスの簡単な説明
- SLO の詳細：目標値と SLI の実装
- エラーバジェットの計算方法と消費のされ方
- **数字の根拠**：実験で決めたのか、観測データから決めたのか。適当に決めたなら、そう書いておく（後の人がその数字を信じて間違った判断をしないように）

見直しは、始めたばかりのうちは頻繁に、安定してきたら間隔をあける。

- 一時点の数字だけでなく、消費のトレンドを見る

## SLO を改善し続ける

### SLO の質を上げる

手動で見つけた障害、問い合わせ、SNS やフォーラムでの苦情などを数えて、エラーバジェットの消費と突き合わせる。

- 障害が起きたのにエラーバジェットが減っていない → SLI のカバレッジが足りない
- エラーバジェットは減っているのに、ユーザーは困っていない → SLI や SLO がユーザー体験とずれている

### SLO とエラーバジェットで意思決定する

「SLO を満たしているか」×「運用の負荷（トイル）」×「顧客の満足度」の組み合わせで次の行動を決める。例：

- 満たしている、トイルは少ない、満足度も高い → リリースを速めるか、もっと信頼性が必要な別のサービスに時間を使う
- 満たしている、トイルは少ない、でも満足度は低い → SLO を厳しくする
- 満たしていない、でも満足度は高い → SLO を緩める

## 発展的なトピック

- **ユーザージャーニーをモデル化する**：個々のリクエストではなく、ユーザーがやりたい一連の操作（クリティカルユーザージャーニー）を単位に考える。例：ネットショップの「商品を検索 → カートに入れる → 購入する」
- **操作の重要度で分ける**：すべてのリクエストが同じ重要度ではない。例：ユーザーが画面の前で待っているリクエストと、裏で先読みするリクエストは別の SLO にする
- **依存関係をモデル化する**：サービスの信頼性は、依存先の信頼性に制約される
- **SLO を緩める実験をする**：ユーザーが本当に必要としている信頼性を知るために、意図的に品質を落として利用状況の変化を見る

## ロードマップの「学ぶ観点」との対応

| 観点                                  | Workbook で分かったこと                                                  |
| ------------------------------------- | ------------------------------------------------------------------------ |
| 1. ユーザーの行動から始める           | クリティカルユーザージャーニーを単位に考える                             |
| 2. SLI の種類                         | SLI メニューで「鮮度」「正しさ」「カバレッジ」「品質」まで整理された     |
| 3. どこで測るか                       | SLI の仕様と実装を分け、品質・カバレッジ・コストで実装を比べる           |
| 4. 目標値は現状を測ってから決める     | 直近の実測値を最初の SLO の出発点にしている（下のメモ参照）              |
| 5. エラーバジェットの使い道           | エラーバジェットポリシーとして、使い切ったときの行動を事前に合意しておく |
| 6. SLO アラートと原因アラートを分ける | 本章では扱わない。SRE Workbook 第 5 章「Alerting on SLOs」               |

### メモ：第 4 章との違い（観点 4）

- 第 4 章：「現在の性能を基準に目標を選ばない」
- Workbook：直近の実測値をもとに最初の SLO を置く

矛盾ではなく、段階の違いと理解しておく。

- 第 4 章が警告しているのは、現状値を**考えずにそのまま**目標として固定すること
- Workbook は、現状値を**スタート地点**として置き、ユーザーの満足度と突き合わせて締めたり緩めたりしていく
- つまり「現状値は出発点、ゴールはユーザーの必要から決める」

## PhysiFun に当てはめて考えたいこと

答えはまだ書かない。`docs/design-logs/physifun-slo.md` で検討するときの問いとして残す。

- **SLI メニューに当てはめる**：ロードマップの 4 つの候補は、それぞれどの種類？
  - 応募フォームの送信成功率 → リクエスト駆動の可用性？
  - 運営審査画面の p95 レイテンシ → 「閾値より速かった割合」の形に書き直すと？
  - Outbox のメール送信遅延 → パイプラインの鮮度？
  - cron ジョブの成功率 → パイプラインのカバレッジ？正しさ？
- **仕様と実装**：応募フォームの成功は、どこで測る？（Vercel のログ、Supabase のログ、ブラウザ側の計測、合成監視）それぞれ何を見逃す？
- **時間窓と母数**：4 週間のローリング窓で、応募は何件ある？例えば 50 件で SLO 99% なら、エラーバジェットは 0.5 件。1 件失敗しただけで使い切る。これでいいのか？（→ ロードマップの「母数の少なさへの対策」）
- **関係者の合意**：個人開発だと、プロダクトマネージャー・開発者・運用担当が全部自分。運営のメンバーも審査画面のユーザーとして関係者になる？
- **エラーバジェットポリシー**：使い切ったとき、自分は何をする？「機能開発を止めて信頼性に集中する」を自分に課せる？
- **数字の根拠**：PhysiFun の SLO v0 は実測なしで決めることになりそう。その場合「仮置き」だと明記して、いつ見直すかを書いておく
